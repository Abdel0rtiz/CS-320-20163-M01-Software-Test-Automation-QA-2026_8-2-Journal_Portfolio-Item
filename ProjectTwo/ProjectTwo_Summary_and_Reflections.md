## Summary

During Project One, I developed and tested three back-end services for a mobile application: contacts, tasks, and appointments. My approach involved translating the requirements for each feature into JUnit test cases that verified both valid behaviors and conditions that should be rejected. In this way, the tests did not merely confirm that the code executed correctly; rather, they directly validated the constraints established for each service.

For the contact service, the tests verified the limits for the identifier, first name, last name, phone number, and address. For instance, `ContactTest` checks values exactly at the permitted boundaries and uses `assertThrows()` to reject identifiers, names, and addresses that exceed length limits, as well as various invalid phone number formats. It also ensures that unsuccessful update attempts do not alter previously stored values. In `ContactServiceTest`, the tests cover scenarios such as duplicate identifiers, record deletion, field updates, and operations involving non-existent or null identifiers. Furthermore, it confirms that modifying one contact does not affect other records stored within the service.

The same approach was applied to the task service. `TaskTest` validates an identifier of up to 10 characters, a name of up to 20, and a description of up to 50. It also tests for null values, empty fields, and strings that exceed the defined limits. Meanwhile, `TaskServiceTest` verifies that tasks can be added, deleted, and updated; that duplicate identifiers are rejected; and that invalid updates leave the original data unchanged.

The appointment tests also incorporated constraints related to dates. `AppointmentTest` ensures that null or past dates are rejected and that descriptions adhere to the established limits. One particularly significant test modifies the original `Date` object after an appointment has been created and confirms that the stored date remains unchanged. Another test modifies the date retrieved via a getter method and then re-examines the object. These tests demonstrate that the defensive copying implemented in the `Appointment` class effectively protects its internal state.

In total, the six files contain 96 `@Test` methods. An examination of the tests in relation to the six production classes shows that the visible executable paths—both those that succeed and those that result in errors—are exercised. Theoretically, this corresponds to complete line coverage of the provided code, although the files supplied do not include a report generated by a tool such as EclEmma or JaCoCo that would allow for an instrumental verification of this percentage. More importantly, the tests were not designed solely to increase coverage: each set of tests is linked to specific requirements and verifies outcomes through assertions.

## Experience Writing JUnit Tests

To ensure my code was technically correct, I used various types of assertions. For instance, `assertThrows(IllegalArgumentException.class, () -> service.addContact(duplicate));` is used to verify that a duplicate contact is rejected. Then, `assertSame(original, service.getContact("1"));` is used to verify that the original contact remains stored. This combination confirms both that the program rejects the invalid operation and that the failure does not alter existing data.

I also aimed for efficient and maintainable tests. In the service files, I used `@BeforeEach` to ensure a clean state before each test. Additionally, helper methods—such as `assertDetails()` in the contact and task services—allow for the reuse of checks without duplicating large blocks of code. This way, each test maintains a specific purpose, making it easier to identify which requirement is failing when an assertion is not met.

## Reflection on Testing Techniques

The primary technique employed was dynamic unit testing, as the classes and services were executed directly via JUnit. I also utilized boundary value analysis. Test cases verify values exactly at the maximum allowed limits and then introduce values that exceed them. For example, `TaskTest` accepts a 20-character name but rejects a 21-character one. This approach is important because many defects appear precisely around input boundaries.

Another strategy involved combining positive and negative tests. Positive tests demonstrate that the system accepts valid data and correctly executes operations such as adding or updating. Negative tests verify that the software rejects null values, duplicate IDs, excessively long inputs, incorrectly formatted phone numbers, and past dates. These can also be considered regression tests, as the entire suite can be re-run after code modifications to ensure that existing functions continue to operate correctly.

Other techniques were not part of the project. Integration tests would be useful if the services needed to communicate with a database, an API, or other components. System tests would evaluate the entire application, while performance tests could measure response times and behavior under load. Security tests would be necessary to identify vulnerabilities related to authentication, authorization, or data protection. Therefore, unit tests were appropriate for this project, but more complex projects would require a combination of different strategies.

## Reflection on Mindset, Bias, and Discipline

Throughout the project, I adopted a cautious mindset. Rather than assuming the program was correct simply because it functioned with standard data, I actively sought to identify scenarios that could trigger errors. Testing for phone numbers is a prime example: beyond checking for incorrect lengths, I tested for the inclusion of letters, spaces, hyphens, symbols, and non-ASCII numeric characters. For appointments, I also tested past dates and potential external modifications to the `Date` object. This mindset was crucial, as an error within a single class could subsequently compromise the service responsible for storing those objects.

I also made a conscious effort to mitigate the bias inherent in testing one’s own code. As a developer, it is easy to focus primarily on scenarios expected to succeed. To counter this, I designed tests based on the project requirements and deliberately sought out inputs that should trigger errors. Furthermore, following invalid operations, many of my tests verify the state of the objects to ensure that existing data remains unchanged. This approach compelled me to evaluate the code from a more critical perspective.

Finally, I believe that discipline is essential for maintaining software quality. Skipping tests might reduce immediate effort, but it significantly increases the risk of introducing defects and technical debt. In my professional practice, I intend to maintain modular code, incorporate tests when developing new features, re-run the test suite after every modification, and update tests whenever requirements change. It is also important to remember that high test coverage does not automatically equate to high-quality testing; each test must validate a meaningful behavior.

Project One underscored the necessity of aligning tests directly with software requirements. Through unit testing, boundary value analysis, negative scenario testing, and state verification, I was able to systematically evaluate the services for contacts, tasks, and appointments. This experience reinforced the importance of maintaining a cautious mindset, minimizing bias, and exercising discipline—all of which are vital for producing reliable software and avoiding technical debt.
